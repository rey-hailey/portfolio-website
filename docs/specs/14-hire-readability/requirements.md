## 1. 배경 — 2026-10-23 채용 담당자·시니어 PM 관점 전체 리뷰

목표는 하나다: **이 포트폴리오로 서류를 통과한다.** 채용 담당자는 홈에서 3분, 하이어링 매니저는 케이스 1개에서 5분을 쓴다. 1440·390 전체 화면 캡처와 본문 원문을 기준으로, "논리가 한 번에 보이지 않는" 원인을 다음과 같이 확인했다.

### 1.3 잘 되어 있어 건드리지 않는 것

- 13번에서 넣은 '한눈에 보기'(문제/한 일/결과) — 구조는 맞다. 크기만 바꾼다.
- 케이스 본문 6단계(배경 → 문제 정의 → 가설 → 실행 → 결과 → 회고)와 본문 문장.
- About 에세이, 경력 타임라인, `/work` 목록 카드(숫자 있음), 추가 사례 카드.
- 디자인 토큰·절제된 톤. 새 색·폰트·간격 값 없음.

### 1.4 원칙

- **새 문구를 지어내지 않는다(AGENTS.md 7절).** 홈에 새로 보이는 문장은 전부 케이스 본문·frontmatter에 이미 있는 문자열을 인용한다(13번 `work-glance.ts` 방식, Vitest로 검사). 사이트 주인이 써야 하는 칸은 4절에 후보와 함께 `[TODO: 문구]`로 둔다.
- 이미지는 "인과를 보여 주는 그림"(결과 그래프, 개선 전·후)만 크게, 장식 이미지는 작게 또는 제거.

## 2. 사용자 스토리

- US-01: 채용 담당자로서 나는 홈 한 화면에서 케이스마다 **문제 → 한 일 → 결과 숫자**를 보고 어떤 케이스를 열지 고르고 싶다. 왜냐하면 3분 안에 적합성을 판단해야 하기 때문이다.
- US-02: 시니어 PM으로서 나는 주장(강점·일하는 방식)마다 **어느 케이스의 어떤 숫자**가 근거인지 바로 보고 싶다. 왜냐하면 근거 없는 "능력" 문장은 읽지 않기 때문이다.
- US-03: 하이어링 매니저로서 나는 케이스 상세 첫 화면에서 결과 그림을 크게 보고 싶다. 왜냐하면 그래프 한 장이 결과 문단보다 빠르기 때문이다.

## 3. 요구사항 (EARS)

### HIR-R01: 홈 대표 작업 카드에 인과 3줄 + 대표 숫자

- 우선순위: P0 · 스토리: US-01 · 해결: H1·H5
- 요구사항: THE SYSTEM SHALL 홈 대표 작업 카드마다 번호·제목 아래에 **문제 / 한 일 / 결과** 3줄(`src/data/work-glance.ts`의 인용 문장)과 `metrics[0]`(값·라벨)을 보여 준다. 썸네일은 데스크톱 240px(현행), 모바일은 본문 옆 작은 4:3(폭 토큰 `--spacing`×24 이내)으로 둔다.
- 수용 기준:
  - [ ] AC1: 1440·390에서 카드 3개 각각에 문제·한 일·결과·숫자가 보인다(Playwright).
  - [ ] AC2: 3줄 문장은 해당 케이스 MDX 원문 문자열이다(기존 `work-glance.test.ts`가 보장).
  - [ ] AC3: 390에서 홈 전체 높이가 현행(6,349px)보다 줄어든다.
- 검증: Playwright + Vitest

### HIR-R02: 강점 카드 = 주장 + 근거 문장 + 숫자 + 링크, 장식 이미지 제거

- 우선순위: P0 · 스토리: US-02 · 해결: H3
- 요구사항: THE SYSTEM SHALL 강점 3개를 제목(주장) · 설명 · **근거 문장(해당 케이스 회고·결과 원문 1문장)** · **근거 숫자(해당 케이스 `metrics[0]`)** · 사례 링크로 보여 주고, 강점 위 시각 자료(`.strength-visual`)는 제거한다.
- 수용 기준:
  - [ ] AC1: 강점마다 숫자 1개와 `/work/<evidence>` 링크가 있다.
  - [ ] AC2: 근거 문장은 evidence 케이스 MDX에 존재하는 문자열이다(Vitest).
  - [ ] AC3: 홈에서 `.strength-visual` 요소가 0개다.
- 검증: Playwright + Vitest

### HIR-R03: 이렇게 일합니다 설명을 문장으로

- 우선순위: P0 · 스토리: US-02 · 해결: H4
- 요구사항: THE SYSTEM SHALL `workingStyle[].description`을 장표 조각 대신 **케이스 본문에 있는 완결 문장**으로 바꾸고, 숫자는 별도 칸(값·라벨)으로 분리해 보여 준다.
- 적용할 원문 (사이트 주인 확인 필요, 모두 본문에 이미 있는 문장):
  1. 원인은 데이터와 사용자 목소리로 확인합니다 → "완료율이 가장 낮던 활동의 원인을 데이터와 사용자 인터뷰로 좁히고, 책 속 핵심 문장을 먼저 따라 말하게 한 작은 변경이 완료율을 20%p 넘게 끌어올렸습니다." · 숫자 `49.7 → 69.8%` Sentence Practice 완료율
  2. 지표를 먼저 정하고 끝까지 추적합니다 → "판매 1건당 매출을 지표로 먼저 잡아 둔 덕분에, 적은 판매 건수로도 성과를 분명히 보여 줄 수 있었습니다." · 숫자 `약 14배` 판매 1건당 발생 매출
  3. 파트너가 팔 수 있는 구조로 상품을 만듭니다 → "OUP가 실제로 파는 건 교과서인데 우리에게는 교과서 상품이 없다는 사실에서 출발해, 학습법·플랫폼·계약이라는 세 벽을 하나씩 풀었습니다." · 숫자 `+40%` ORC 매출 전년 동기 대비
  4. 개발을 기다리지 않고 직접 만듭니다 → "외주였다면 작가 · 일러스트 · 성우 · EPUB 4곳 · 수개월이 걸렸을 일을 1명 · 약 2개월로 줄였습니다." · 숫자 `2주 · 36권` 3개 언어 납품
- 수용 기준:
  - [ ] AC1: 4개 설명이 모두 마침표로 끝나는 문장이고 ` · `로 이은 조각이 아니다(Vitest).
  - [ ] AC2: 각 설명은 work MDX 또는 `work-briefs.ts`에 존재하는 문자열이다(Vitest).
- 검증: Vitest

### HIR-R04: 히어로 숫자 4개를 눌러 볼 케이스와 1:1로

- 우선순위: P0 · 스토리: US-01 · 해결: H2
- 요구사항: THE SYSTEM SHALL 홈 `metrics` 4개를 모두 공개 케이스 `metrics`에 있는 값으로 두고, 각 숫자를 해당 케이스 상세로 링크한다. 괄호 단서("인건비 제외")는 히어로에서 빼고 상세의 note에만 둔다.
- 제안 (사이트 주인 선택):
  | 칸 | 현행 | 제안 A (권장) | 제안 B |
  |---|---|---|---|
  | 1 | +11.1%p 활동 완료율 | 54.5 → 65.6% 활동 완료율 (North Star) → `/work/laura` | +11.1%p (현행) |
  | 2 | +40% ORC 매출 | +40% ORC 매출 · 전년 동기 대비 → `/work/orc-laura` | 동일 |
  | 3 | 16% 중국 비중 | 약 14배 판매 1건당 발생 매출 → `/work/orc-laura` | 0 → 16% (BRC는 상세 없음, 링크 불가) |
  | 4 | ROI 2,400% (인건비 제외) | 1명 · 약 2개월 · 12권 출간 → `/work/the-life-of-our-lord` | 25배 투입 비용 대비 매출 |
- 수용 기준:
  - [ ] AC1: 4개 값 문자열이 공개 work `metrics` 또는 본문에 존재한다(Vitest).
  - [ ] AC2: 각 숫자가 `/work/<slug>` 링크다(Playwright).
- 검증: Vitest + Playwright

### HIR-R05: 상세 상단 결과 그림을 크게, 중복 썸네일 제거

- 우선순위: P0 · 스토리: US-03 · 해결: W1
- 요구사항: THE SYSTEM SHALL '한눈에 보기'의 결과 그림을 3줄 아래 본문 전체 폭(`wide`, 13번 WRR-R03과 같은 규칙)으로 보여 주고, 요약 박스 아래의 큰 썸네일(`.thumb-frame`)은 상세에서 제거한다(목록 카드·OG에는 유지).
- 수용 기준:
  - [ ] AC1: 1440×900 첫 화면에 결과 그림이 본문 폭(≥ 680px)으로 보인다.
  - [ ] AC2: 상세에서 `transition:name="work-thumb-*"` 이미지가 0개다. 목록 → 상세 View Transition은 제목만 이어진다.
  - [ ] AC3: 가로 스크롤 없음(6개 너비, FND-R10).
- 검증: Playwright

### HIR-R06: 같은 사실은 한 가지 숫자로

- 우선순위: P1 · 해결: W2
- 요구사항: THE SYSTEM SHALL 한 사실에 한 표현만 쓴다. LAURA 그래프 캡션에 "월별 값 · 기간 평균 54.5 → 65.6%"를 붙여 요약 박스와 맞추고, LOOL은 "투입 비용 대비 매출 25배" 하나로 통일한다(ROI 2,400%·약 4%는 note로 내린다).
- 수용 기준:
  - [ ] AC1: LOOL 상세·홈·목록에서 같은 사실의 표기가 1개다(수동 확인).
- 검증: 수동 확인 · **표현 선택은 사이트 주인 확인 필요**

### HIR-R07: 회귀

- 우선순위: P0
- 요구사항: THE SYSTEM SHALL `pnpm build`·`pnpm test`·e2e(responsive·home·work)를 통과하고 Lighthouse 4항목 0.95 이상을 유지한다. 새 색·폰트·간격 값 없음, 새 npm 의존성 0.

## 4. 사이트 주인이 써야 하는 문구 (코드로 못 고치는 것)

아래는 **제가 지어내지 않는** 칸이다. 후보는 참고용이며, 고르거나 다시 쓰면 그대로 반영한다.

| 위치 | 현행 | 왜 바꾸는가 | 후보 (참고) |
|---|---|---|---|
| 히어로 직함(eyebrow) | AI Product Manager · Global Project Manager | 검색·스캔 키워드는 "AI PM"이다. 뒷부분이 포지셔닝을 흐린다 | `AI Product Manager · 에듀테크 · 글로벌 B2B` |
| 히어로 부제(`home.problem`) | 사용자 행동 데이터로 학습 경험을 개선하고, 파트너의 판매 방식에 맞춰 AI 상품을 출시했습니다. | H1 반복. "어떤 문제를 푸는 PM인가"가 빠져 있다 | `아이가 끝까지 하게 만드는 학습 경험, 파트너가 팔 수 있는 AI 상품 — 두 문제를 숫자로 풀어 왔습니다.` |
